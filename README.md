# CovLedger

**Python test evidence and code-quality signals for coding agents.**

CovLedger runs pytest with Coverage.py, records one replaceable current analysis in a disposable checkout cache, and helps developers choose the next behavior to test. It is a Python-only experiment inspired by Supercov's focus on actionable test evidence.

The current MVP supports Python 3.12+, pytest, line and branch coverage, deterministic AST quality facts, and optional semantic quality judgments through PyJev. It does not claim MC/DC or assertion coverage, arbitrary test-runner support, or an owned `sys.monitoring` collector.

## Development

CovLedger uses a flat package layout (no `src/` directory):

```bash
python -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[dev]'
pytest
```

Versioning is dynamic through `setuptools-scm`; Git tags are the source of truth:

```bash
git tag v0.1.0
python -m build
```

`covledger/_version.py` is generated by `setuptools-scm` and is intentionally not committed.

## Initialize and run

Initialize CovLedger once per project, then run the project's pytest suite through CovLedger:

```bash
covledger init
covledger run -- pytest -q
```

`init` registers CovLedger with LedgerCore's `cache` mount, creates the project configuration if it is missing, and prints the resolved cache path. `run` reports the analysis ID, suite status, and coverage summary, and returns pytest's exit code. A failed suite still produces a current result describing the failure; `next` will not select work from a failed suite.

Run accepts pytest arguments (for example, `covledger run -- python -m pytest -q`). The command uses the Python interpreter running CovLedger and does not persist pytest output.

## Current analysis

A completed run publishes one `current.json` in LedgerCore's checkout-scoped cache. These commands use that result without rerunning pytest:

```bash
covledger overview
covledger findings --min-score 70
covledger next
covledger inspect F-xxxxxxxxxx
covledger inspect Q-xxxxxxxxxx
covledger inspect G-xxxxxxxxxx
```

`overview`, `findings`, `next`, `inspect`, and `report` require a current analysis whose source hashes and analysis-affecting configuration still match the checkout. CovLedger reports a stale result instead of combining old coverage with changed source. Rerun tests to replace it. `inspect` reads source from the live project and verifies its hash before showing an excerpt; it never reads a source snapshot.

Function IDs use the `F-` namespace, findings use `Q-`, and coverage gaps use `G-`. `findings` also supports filters such as `--band`, `--file`, `--kind`, `--rule`, and `--semantic`. JSON output is available with `--json` on the current-analysis query commands.

Priority scores combine deterministic quality and coverage evidence. Optional PyJev judgments remain separate from exact facts and are not treated as zero evidence when absent. InferLingo applies package-owned exact rules and provenance to derived labels and proof paths; it does not parse source, calculate coverage, or assign numeric priority.

## Quality analysis

`quality` analyzes current source independently of a coverage run and does not publish `current.json`:

```bash
covledger quality
covledger quality src --semantic
```

It honors the configured analysis scope and reuses content-addressed semantic results from LedgerCore's cache. PyJev authentication and credentials follow PyJev's own configuration.

The bundled semantic rules describe properties such as hidden side effects, too many conceptual jobs, surprising mutation, implicit process state, hidden I/O, policy/mechanism mixing, ambiguous error contracts, and misleading names. See `covledger/quality_rules.toml` for the exact rule set.

## Project policy and explicit decisions

`.ledger/covledger/config.toml` is CovLedger's durable project policy. It is appropriate to commit because it expresses what the project wants analyzed, not generated findings. For example:

```toml
config_version = 2

[ledger]
code = "cov"
name = "covledger"

[coverage]
branch = true

[quality]
semantic_threshold = 0.70

[analysis]
include = ["src"]
exclude = ["examples", "context_*.unpack.py"]
include_generated = false

[priority]
high = 70
critical = 85

[[decision]]
symbol = "src/module.py:wrapper"
action = "ignore"
reason = "Intentional presentation-only wrapper"
```

An empty `analysis.include` list means all otherwise eligible project source; a non-empty list is an allowlist. Exclusions are applied after includes, so they always win. Directory rules apply recursively. Generated-source detection is controlled by `include_generated`; it does not bypass explicit exclusions. The same scope policy applies to coverage, deterministic and semantic quality, assessment, and reports. It does not change pytest collection or the test command.

Decisions are explicit user preferences and match stable relative-path/qualified-function symbols, not line numbers. Use `action = "ignore"` to omit a function from prioritization, or `action = "ignore-finding"` with a `rule` to suppress one finding for that function. Each decision requires a reason. Machine-generated classifications remain derived cache data unless a user records an explicit decision.

## Storage and persistence

CovLedger follows one rule: **persist project intent, cache replaceable computation, and do not keep run history.**

The checkout contains the project configuration and LedgerCore registration/ownership metadata. CovLedger registers only a LedgerCore `cache` mount. The actual cache location is platform- and checkout-specific; CovLedger obtains it from LedgerCore rather than constructing a path. Inspect it with:

```bash
covledger cache path
```

The cache contains the single `current.json`, reusable semantic entries under `jev/`, and temporary `work/` files while a run is in progress. Temporary Coverage.py databases and reports are removed after the run. Current analysis stores source hashes and compact findings/gaps, not copies of source code.

The cache is disposable. Clear CovLedger's cache contents while preserving LedgerCore's ownership binding with:

```bash
covledger cache clear
```

Removing the entire resolved cache also loses no project policy or decisions; CovLedger will need to recompute its analysis and semantic judgments. There are no immutable run directories, history selectors, run-to-run diffs, or automatically archived reports. If an existing project is migrated from the recognized legacy `runs` mount, CovLedger leaves that external data untouched and stops using it; remove it manually only when you decide it is no longer needed.

## Reports are exports

Generate a report from the fresh current analysis. Markdown is the default; both formats go to stdout unless an output path is explicitly requested:

```bash
covledger report --format md
covledger report --format csv
covledger report --format md --output report.md
```

Reports include prioritized functions, priority and attention band, finding/gap IDs, source location, qualified function, rationale, deterministic and semantic findings, and a suggested action. CovLedger does not save a report in the project or cache automatically; an explicitly requested output file is user-owned.

## Design invariants and limitations

1. Unknown evidence is not silently treated as covered.
2. A failed suite is visible in the current result and blocks `next`.
3. Current results are freshness-checked against source hashes and analysis-affecting configuration.
4. Machine-derived observations are disposable; only project policy and explicit user decisions are durable.
5. Semantic judgments keep their probabilities; thresholding is CovLedger policy, not model truth.
6. JSON output is a public contract from the first version.

Coverage collection delegates to Coverage.py. The intended learning path is to keep that backend as a differential oracle while exploring an owned `sys.monitoring` backend.
